# 사용자별 3D 인증·저장 통합과 migration 승인 자료

이 문서는 배포 절차이며 운영 DB 변경을 실행하지 않는다. 통합 코드의 기본 스키마는 `public`이다. 기존 `users`의 ID·bcrypt 해시와 `swings`의 소유권을 그대로 사용한다. 실험 스키마에서 사용자 계정을 복사하는 방식은 포함하지 않는다.

## 확인한 운영 상태와 영향

2026-10-28 읽기 전용 사전 점검에서 기존 public revision은 `0002`, users 8행, swings 20행이었다. 진행 중 분석은 0건이고 기존 users/swings RLS가 활성화돼 있었다. 기존 계정 `testuser01`은 존재했다. 소유자 없는 swings 7행은 이번 통합에서 임의로 배정하지 않는다. 관리자가 원본 증거와 동의를 확인하는 별도 소유권 검토가 필요하다.

이 수치는 사전 점검 스냅샷이다. 승인 후 적용 직전에 다시 확인한다. 운영 migration이나 운영 로그인·업로드를 수행했다는 의미가 아니다.

기존 운영 환경 변수에 지정된 Storage 버킷도 읽기 전용 GET으로 확인했다. 비공개이며 별도 MIME 제한은 없었다(따라서 application/gzip을 제한하는 설정은 없었음). 공유 storage.objects 정책은 사전 점검 시 0개였다. 버킷 설정·정책·파일은 변경하지 않았다. 배포 직전에 다시 점검한다.

| 변경 | 범위·영향 |
|---|---|
| Alembic `0003` | `auth_sessions`, `pose_3d` 두 테이블과 인덱스·FK만 추가 |
| 기존 데이터 | users/swings의 행, 비밀번호 해시, 분석 점수·피드백 변경 없음 |
| 참조 | auth_sessions.user_id → users.id, pose_3d → swings.analysis_id 및 users.id |
| 직접 DB 접근 | 새 두 테이블 RLS 활성화, 존재하는 anon/authenticated 역할의 새 테이블 권한만 제거 |
| 앱 인증 | 기존 bcrypt 로그인 후 난수 Bearer 세션 발급, DB에는 SHA-256만 저장, 기본 8시간 만료·로그아웃 폐기 |
| API 호환성 | 기존 로그인 응답에 토큰 추가. 업로드·내 정보·기록·분석·영상·3D는 Bearer 필요. 구 클라이언트의 무인증 접근은 401 |
| 과거 분석 | 본인 기록과 영상·점수 유지. 기존에 3D가 없는 분석은 404 안내, 자동 재추론·샘플 대체 없음 |
| 소유권 | 본인만 200, 다른 소유자·소유자 없는 분석 403. 호출자가 user_id를 바꿔 권한 획득 불가 |

서버 시작은 migration을 자동 실행하거나 테이블을 생성하지 않는다. 새 테이블이 없으면 시작 검사에서 실패하므로 백엔드와 Flutter를 한 배포 단위로 적용한다. 워커 복구는 기존 규칙대로 같은 `SWING_WORKER_ID`의 중단된 분석·3D 작업만 실패 처리한다. 운영 검증용 서버를 같은 worker ID로 추가 실행하지 않는다.

## 승인 전 준비와 백업

1. 운영 DB/버킷/배포 대상, 현재 Alembic revision, 활성 작업, 앱 버전을 기록한다. 연결 문자열·서비스 키·사용자 값은 보고서나 PR에 저장하지 않는다.
2. Supabase 관리 백업 또는 `pg_dump`로 해당 DB의 schema/data를 보호된 저장 위치에 백업한다. 기존 users/swings/제약/권한과 alembic_version을 포함하고 별도 비운영 DB에 복구 가능한지 확인한다. 비밀번호를 명령줄 인수에 넣지 않는다.
3. 기존 private 영상 버킷을 재사용할지, 승인받은 별도 비공개 버킷을 사용할지 결정한다. 새 버킷을 쓰면 기존 영상의 DB bucket 참조가 유지되는지 검증한다. 기존 파일을 이동하거나 삭제하지 않는다.
4. staging에서 기존 DB 구조와 `0002 → 0003` 이행을 검증한다. `alembic upgrade 0002:0003 --sql`로 추가 SQL을 검토한다. SQL 생성은 실행이 아니다.
5. 이 영향 범위와 백업·복구 결과를 사용자/관리자에게 제시하고 **운영 migration 승인을 받는다**. 이 PR의 생성·push 권한은 운영 DB 변경 승인을 대신하지 않는다.

## 승인 후 운영 적용 절차 — 현재 미실행

1. 짧은 배포 창에 새 업로드를 멈추고 기존 작업 종료를 확인한다. 승인된 배포 프로세스만 종료한다.
2. 기존 비밀 설정으로 `DATABASE_URL`, `SWING_DATABASE_SCHEMA=public`, 비공개 `SUPABASE_STORAGE_BUCKET`, `SWING_STORAGE_BACKEND=supabase`를 지정한다. 정확한 프론트 origin을 `SWING_CORS_ORIGINS`에 지정하고 HTTPS를 사용한다. 테스트 스키마/버킷 값을 운영 설정에 복사하지 않는다.
3. 현재 revision이 정확히 `0002`인지 확인한 뒤 `alembic upgrade 0003`를 실행한다. 기존 DB를 fresh DB로 간주하거나 revision을 임의 stamp하지 않는다. `0001/0002`는 이미 적용된 기존 migration이다.
4. 새 테이블/외래키/인덱스/RLS와 기존 사용자·분석 집계가 보존됐는지 확인한다. PostgreSQL은 두 새 테이블을 트랜잭션 안에서 추가하며 FK 생성에는 참조 테이블에 짧은 잠금이 필요하다. 운영자가 lock_timeout을 정하고 장기 트랜잭션과 충돌하면 취소·재검토한다.
5. 새 백엔드와 Flutter를 함께 배포하고 기존 계정 정상 로그인, 다른 계정 403, 무인증 401, 기존 기록/영상, 새 좌타·우타 업로드와 3D 조회를 검사한다. 새 표시는 기존 점수의 성공/실패 상태와 독립이다.

## Storage 권한 검증

서버는 private bucket 여부를 실제 Storage API로 확인하며 공개 버킷에는 업로드하지 않는다. 3D 객체는 인증·소유권 검사가 끝난 FastAPI가 제한된 크기로 읽고 SHA/분석 ID를 검사한 뒤 JSON으로 반환한다. 3D용 공개 URL이나 signed URL을 클라이언트에 전달하지 않는다. 원본 영상은 기존과 같이 소유권 확인 후 짧은 signed URL을 발급한다.

이 앱의 Bearer는 Supabase Auth JWT가 아니다. `auth.uid()`와 앱 users.id를 같은 값으로 가정하는 RLS를 만들지 않는다. Storage service-role 키는 백엔드에만 두며 Flutter에 넣지 않는다.

기존 공유 `storage.objects`의 정책을 먼저 읽기 전용으로 검토한다. 기존 검증 시점에는 정책 0개·RLS 활성화로 일반 역할 접근이 차단됐지만 운영 적용 때 다시 확인해야 한다. 무인증 다운로드, anon 역할, authenticated 역할, 다른 앱 계정의 API 접근을 각각 검증한다. 실제 anon/Auth JWT HTTP 검증을 수행하지 않았다면 DB 역할 검사와 구분해 미검증으로 기록한다.

광범위한 허용 정책 때문에 대상 버킷의 일반 클라이언트 접근이 가능하면 `migrations/storage_backend_only.sql`의 제한 정책을 검토한다. 이는 **기존 공유 Storage 테이블의 정책 추가**이므로 버킷 이용자 영향과 별도 승인이 필요하다. placeholder를 실제 승인된 bucket으로 바꾸기 전에는 실행하지 않는다. 기존 정책을 삭제하거나 통째로 대체하지 않는다. 정책은 다른 bucket에는 조건상 영향이 없지만 대상 bucket의 기존 클라이언트 직접 접근은 차단한다.

## 롤백

권장 긴급 롤백은 배포 앱/서버를 이전 버전으로 되돌리되 두 새 테이블·private 3D 객체를 보존하는 방식이다. 기존 데이터 구조에 열을 추가하지 않으므로 구 코드에 영향을 최소화한다. 구 백엔드에는 기존 무인증 접근 문제가 있으므로 외부 접근을 제한한 유지보수 상태에서 조치한다.

DB downgrade는 세션과 3D 메타데이터를 삭제하므로 자동 실행하지 않는다. 별도 승인과 새 테이블 백업 후 정확히 `alembic downgrade 0002`만 수행하면 새 두 테이블만 제거한다. `0001/base`까지 내리지 않는다. 기존 users/swings는 변경하지 않고 Storage 객체도 삭제하지 않는다. 다시 배포할 계획이면 downgrade 없이 추가 테이블을 보존하는 쪽을 권장한다.

선택적 Storage 정책을 실제 추가했다면 별도 승인 후 해당 정책 이름 하나만 되돌린다. 버킷·원본 영상·기존 사용자·실험 계정은 정리 작업에 포함하지 않는다. 새 객체의 저장 실패로 고아 객체가 생길 수 있으므로 향후 정리 작업은 DB 참조 감사와 별도 승인 하에 수행한다.

## 남은 운영 조건

공개 배포 전 로그인 rate limiting/계정 복구, 세션 관리, HTTPS·정확한 CORS, 모바일 네트워크와 기기 렌더링을 추가 검증한다. 현재 메모리 세션은 브라우저 새로고침 후 다시 로그인한다. 단일 프로세스/단일 추론 워커 전제는 유지된다. 자동 기하·표시 품질 개선은 실제 3D 정답에 대한 정확도 보증이 아니다.
