# 피드백 API 작업 노트

작성일: 2026-09-24 / 브랜치: `feat/feedback-api`

사용자 스윙 영상을 기준 스윙 모델과 비교해 **종합 / 관절별 / 구간별** 피드백을 돌려주는 API를 만들면서
확인한 내용과, 앞으로의 설계 방향을 정리한 문서입니다.

---

## 1. 지금 구현한 것

```
POST /analyses          영상 + 좌우타 → 작업 등록(202)
POST /analyses/features 추출된 .npy 로 바로 비교 (영상 없이 테스트용)
GET  /analyses/{id}            상태 + 전체 결과
GET  /analyses/{id}/overall    종합 피드백
GET  /analyses/{id}/joints     관절별 피드백 (각도 7개)
GET  /analyses/{id}/phases     구간별 피드백
```

코드 구조

| 폴더 | 내용 |
|---|---|
| `feedback/pipeline.py` | 영상 → 스켈레톤 → 80x67 피처. 기존 `process_video` 와 같은 순서(확인용 `imshow` 제거, 실패 시 예외) |
| `feedback/reference.py` | `reference_templates.npz` 로딩, 구간 경계 검출, 점수 환산 기준 |
| `feedback/compare.py` | DTW 비교 후 종합/관절별/구간별 수치 계산 |
| `feedback/features.py` | 64개 피처의 인덱스와 이름 정의 |
| `api/` | 앱 조립(main.py), 회원 라우터, 피드백 라우터, 작업 큐(워커 1개), 응답 스키마 |
| `tests/test_api.py` | `.npy` 업로드 경로로 API 전체 흐름 검증 |

비교 단계는 기존 DTW 모듈을 그대로 사용합니다.
`transform_feature_sequence` → `dtw_distance` → `align_sequence_to_template_timeline` 순서로,
`align_individual_features_to_template.py` 와 같은 방식입니다.

기존과 다른 점은 두 가지입니다.
- 임팩트 판정 전에 관절 좌표를 기준 fps(기본 30)로 리샘플링합니다.
- 정렬 결과로 점수/각도 차이/구간 수치를 계산합니다. (기존은 거리 값과 정렬된 `.npy` 저장까지)

실행

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn api.main:app --reload   # 문서: http://127.0.0.1:8000/docs
.venv/bin/python -m pytest tests
```

`mediapipe` 는 1.0.x 에서 `pose_landmarker.task` 로드 시 크래시가 나서 `<1` 로 고정했습니다.

## 2. 확인한 문제 (데이터 근거 포함)

### 2-1. 기준 템플릿 앞부분이 실제 동작이 아니다

- 영상 데이터가 1~2초인데 `features_add.py` 는 임팩트 **앞 60프레임(30fps 기준 2초)** 을 자릅니다.
  모자란 앞부분은 첫 프레임을 복사해서 채웁니다.
- 선수별 템플릿 37개 중 16개에서 앞쪽 프레임 값이 **완전히 동일**합니다(최대 35프레임).
  선수당 스윙 8개 이상의 평균이므로, 그 선수의 스윙 전부가 복사 프레임이었다는 뜻입니다.
- global 템플릿에서 손 이동량 비중: 0~31프레임 **1.6%**, 32~53 24.0%, 54~59 27.2%, 60~79 47.2%.
- 프레임 간 관절 변화량이 31→32 프레임에서 0.02 → 0.18 로 계단처럼 뜁니다(복사 프레임이 끝나는 지점).

### 2-2. DTW 가 시간축을 거의 맞추지 않았다

- 템플릿 생성 시: 스윙 1개당 대각선을 벗어난 대응이 **평균 1.4프레임 / 80프레임**. 선수 37명 중 10명은 0.
- 사용자 영상 비교 시: DTW 경로가 **완전한 대각선**. 그래서 구간 템포 비율이 항상 1.0 근처로 나옵니다.
- 원인: 임팩트가 이미 60프레임에 맞춰져 있고, 경로를 틀면 비용이 추가되며,
  Sakoe-Chiba 밴드 15%(±12프레임) 제한도 있습니다.
- 결과적으로 기준 모델은 **임팩트 한 시점만 정렬된 평균**입니다.
  나머지 동작(착지, 스윙 시작 등)은 스윙마다 다른 시점의 자세가 같은 프레임 번호끼리 평균되었습니다.

### 2-3. 구간 경계에 근거가 없다

- 현재 API 의 구간(준비 0~32 / 로딩 32~54 / 스윙 54~60 / 팔로우 60~80)은
  템플릿 손목 속도로 검출한 값이지만, 임계값(5배, 50%)은 임의로 정한 값입니다.
- 특히 경계 32는 동작이 아니라 **복사 프레임이 끝나는 지점**입니다.
- 참고: 삭제된 이전 코드(`swing_comparator.py`, 커밋 `b734e3a` 에서 제거)에는
  `PHASES = {address:(0,15), loading:(15,35), stride:(35,50), pre_impact:(50,60), impact:(60,64), follow_through:(64,80)}`
  가 있었습니다. 이것도 고정 프레임 번호이며 근거는 기록되어 있지 않습니다.

### 2-4. 기타

- **피처 개수 불일치:** 파이프라인은 67개를 만들고 템플릿은 64개입니다.
  속도 3개(골반/어깨 회전 속도, 손목 속도)가 템플릿에 없어 비교에서 제외됩니다.
- **종합 점수가 품질을 반영하지 못함:** 입력의 절반 이상이 복사 프레임인 영상도 80점대가 나옵니다.
  현재 점수 기준(프로 스윙 1개가 기준에서 떨어진 거리)은 템플릿 편차로 **추정**한 값입니다.
  삭제된 이전 코드에는 `mean_own_template_distance` 로 보정하는 공식이 있었으나, 현재 npz 에는 그 값이 없습니다.
- **각도 0° 아티팩트:** `_calculate_angle` 이 계산 실패(NaN)를 0으로 바꿔서, 그 값이 비교에 섞입니다.
- **"회전" 명칭:** 62/63번 피처는 좌우-상하 평면에서의 **기울기**이며 세로축 회전량이 아닙니다.
  `_compute_all_velocities` 의 회전 속도도 같습니다.
- **템플릿 원본 fps 미확인:** 현재 기준 fps 30은 가정입니다.

### 2-5. 테스트 영상 2개 결과

`NC_86_박민우.mp4`(30fps), `LG_67_문보경.mp4`(30fps) 로 전체 경로를 실행했습니다. 처리 시간은 11~18초.

- 두 영상 모두 파일 정보상의 프레임 수보다 실제로 디코딩되는 프레임이 적습니다(167→73, 37→30).
- 박민우: 복사 프레임 11개, 종합 81.9점. 문보경: 복사 프레임 50개(앞 46), 종합 82.6점.
- 문보경 결과의 주요 문제점 3개는 모두 복사 프레임 구간이거나 검출 오류(앞다리 무릎 9.6°)였습니다.

## 3. 앞으로의 방향: 이벤트 기반 정렬

고정 80프레임 + DTW 대신, **동작 사건(이벤트)** 으로 시간축을 맞춥니다.

```
영상 → 스켈레톤 추출(촬영 fps 그대로)
     → 이벤트 감지 (로딩 시작 / 앞발 착지 / 스윙 시작 / 임팩트 / 팔로우 종료)
     → 구간별 0~100% 시간 정규화
     → 비교
```

- **구간 위치·길이**: 실제 시간(ms)으로 비교 → 템포/리듬 피드백
- **자세(각도)**: 구간별 정규화 후 같은 진행률끼리 비교 → 순수 자세 차이
- **속도 지표**: 정규화 전 실제 시간 기준으로 계산 (스윙 시간, 최대 손 속도, 회전 속도, 꼬임 순서)

이 방식의 장점
- 복사 프레임이 필요 없습니다. 이벤트를 못 찾으면 그 구간을 "분석 불가"로 표시합니다.
- fps 가 달라도 비교할 수 있습니다(60fps 촬영 그대로 활용 가능).
- 스타일 차이(긴 로딩)와 실력 차이(느린 스윙)를 구분할 수 있습니다.

### 기준 모델을 다시 만들어야 하는 이유

현재 템플릿은 80프레임 평균 곡선 하나라서, 스윙 단위 정보가 남아 있지 않습니다.

| 필요한 값 | 현재 템플릿 |
|---|---|
| 이벤트 시점 / 구간 길이의 평균·편차 | 없음 |
| 구간별 진행률 기준 자세 곡선 | 없음 (프레임 번호 기준이며 복사 프레임 포함) |
| 속도 지표 분포 | 없음 (평균 곡선에서 계산하면 최대값이 뭉개짐) |

→ 원본 영상 300개 또는 스윙별 `.npy` 로 **사용자와 동일한 규칙**을 적용해 다시 만들어야 합니다.

## 4. 팀에 확인이 필요한 사항

1. 템플릿을 만든 원본 영상의 **fps** (30/60/혼합 여부)
2. 스윙별 원본 피처 `.npy` 폴더 (템플릿 재생성과 점수 기준 보정에 필요)
3. 템플릿 `.npy` 를 만든 코드 버전 — 현재 파이프라인 결과와 값의 스케일이 달라 보입니다
   (예: 임팩트 시점 손 위치 깊이값이 사용자 -0.5 vs 기준 -9.4, 어깨 라인 기울기가 거의 반대 방향)
   → 템플릿에 포함된 영상 1개와 그 `.npy` 를 함께 받아 대조하면 확인 가능합니다.
4. `swing_comparator.py` / `compare_user_swing.py` (커밋 `b734e3a` 에서 삭제)를 **왜** 제거했는지
5. 데이터셋 영상이 1~2초인 이유 — 원본이 더 긴지, 잘라서 저장한 것인지
